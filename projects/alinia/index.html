From search feature to operating system

Property discovery sits inside a larger workflow: listings must be managed, agencies and users need appropriate access, inquiries move across web and messaging channels, and conversations eventually require a person or an operational follow-up.

Alinia was engineered around that full path instead of treating AI search as an isolated interface.

Technical implementation

Alinia separates the public marketplace, transactional application services, AI retrieval services, and messaging operations. The architecture keeps structured listings and authorization rules authoritative while allowing AI to improve how a user expresses, narrows, and continues a property search.

Architecture and discovery flow

  1. 01 · RequestCapture intent and language

    A public search or conversation enters with free-form criteria, locale, and session context; authentication is added only where the workflow requires it.

  2. 02 · Query planningNormalize before retrieval

    Language, location, property type, transaction type, budget, and other supported filters are converted into a structured search plan.

  3. 03 · RetrievalSearch authoritative listing data

    Deterministic filters, text retrieval, semantic retrieval, and reranking can contribute candidates, but returned properties must resolve to stored listing records.

  4. 04 · ExperienceReturn inspectable properties

    The application renders listing attributes, media, agency context, and actions; a model may explain or refine results but does not create inventory.

  5. 05 · OperationsMove inquiry into accountable work

    Customer records, assignments, messaging, staff takeover, CRM activity, and reporting connect discovery to a person or agency workflow.

  6. 06 · FederationSynchronize approved context to Hader

    Approved identity and listing changes cross a controlled federation boundary through provisioning and queued synchronization rather than a shared database.

System invariants

  • Listings remain the source of truth

    An AI response can rank, summarize, or clarify stored properties; it cannot make an unavailable property real.

  • Lifecycle state controls visibility

    Review, approval, publication, reassignment, sale, rental, archive, and deletion behavior determine where a listing may appear.

  • Access follows organizational scope

    Public users, agents, agency administrators, and platform administrators have distinct authentication and authorization paths.

  • Human takeover is explicit

    Messaging can move from automated assistance to a managed staff workflow without losing the originating customer and listing context.

  • Public cache follows listing mutations

    Changes that affect public availability must invalidate or refresh cached discovery data rather than wait for an unrelated expiry.

  • Federated mirrors are not editable inventory

    Hader receives approved listing context through the integration boundary; the originating Alinia records remain authoritative.

Key engineering decisions and tradeoffs

Combine deterministic filters with semantic retrieval
Why: explicit budget, location, and property constraints need predictable filtering, while natural-language requests benefit from broader recall. Tradeoff: the ranking pipeline is more complex than either SQL filtering or embeddings alone.
Short-circuit the model when parsing is already confident
Why: avoids unnecessary model latency and cost for requests that can be converted safely with deterministic extraction. Tradeoff: confidence rules need maintenance as vocabulary and markets evolve.
Keep AI services separate from transactional services
Why: retrieval, reranking, language handling, and model providers can evolve without placing core listing writes inside the inference process. Tradeoff: adds a service boundary, deployment coordination, and fallback behavior.
Cache public listing reads and invalidate on state change
Why: reduces repeated aggregation and media work on high-read discovery routes. Tradeoff: every mutation path that changes visibility must participate in invalidation.
Federate identity instead of duplicating passwords
Why: lets an approved Alinia identity enter Hader without a second credential lifecycle. Tradeoff: key rotation, token validation, deprovisioning, and cross-product failure handling become explicit responsibilities.
Mirror listings through an outbox-style boundary
Why: decouples a listing transaction from Hader availability and preserves a retryable record of the intended change. Tradeoff: the mirror is eventually consistent and needs reset and reconciliation paths.

Failure handling and verification

  • Authorization and invitation checks

    Authentication reality audits, invitation simulations, agency feature enforcement, and role-specific routes test how access changes across user types.

  • Search grounding

    Normalization, location resolution, filter parsing, hybrid retrieval, reranking, and stored-listing resolution keep the discovery path attached to actual inventory.

  • Operational consistency

    Soft deletion, identity merge, state-aware cache invalidation, webhook queues, and scheduled housekeeping address changes that span multiple records or services.

  • Integration recovery

    Federation capability checks, approval and provisioning flows, queued synchronization, reset, and deprovision behavior give the Hader boundary defined recovery paths.

  • Production performance work

    Pagination, parallelized reads, reduced duplicate listing fetches, and targeted cache busting came from observed production behavior rather than synthetic speed claims.
