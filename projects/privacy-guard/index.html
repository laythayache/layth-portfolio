PrivacyGuard

A Python pipeline for detecting and masking selected sensitive regions in images, recorded video, and live streams before downstream use.

View the repositoryTechnical implementationRead the fact-checked field note

Technical implementation

PrivacyGuard is a public Python implementation built around OpenCV, ONNX Runtime, and compatible detection models. It separates detection from transformation: a detector proposes labeled regions, policy selects which detections qualify, an anonymizer modifies only those regions, and the surrounding pipeline decides whether the result is returned, written, streamed, profiled, or audited. That separation makes the masking behavior inspectable without pretending that detection is infallible.

Frame-processing flow

  1. 01 · InputNormalize the media source

    An image, recorded video, camera, or network stream is converted into frames with validated dimensions and processing configuration.

  2. 02 · DetectionProduce typed candidate regions

    A selected local detector or ensemble returns bounding regions, class labels, and confidence values; optional regional detectors can add document, text, or plate candidates.

  3. 03 · PolicyFilter what should be transformed

    Target classes, label mapping, confidence thresholds, and custom regions decide which candidates enter the masking stage.

  4. 04 · TransformationModify only the selected regions

    The anonymizer applies Gaussian blur, pixelation, or solid occlusion using validated parameters while leaving the remainder of the frame unchanged.

  5. 05 · OutputReturn or encode the processed frame

    Image, batch, video, live-stream, API, and command-line paths reuse the same core detection-and-mask contract.

  6. 06 · ObservationMeasure and record processing behavior

    Optional profiling, monitoring, audit records, metadata stripping, and status markings can be attached without changing the detector interface.

System invariants

  • No detection means no guaranteed mask

    The transformation stage cannot hide a face, person, plate, document, or text region that the selected detector failed to identify.

  • Policy is separate from model output

    A detected class is not automatically modified; configured targets and thresholds determine whether masking is applied.

  • Masking is not encryption

    Blur and pixelation alter visible pixels, while solid masking occludes a region; none of these operations proves that the source or other metadata cannot be recovered elsewhere.

  • Local is the default processing boundary

    The core pipeline can run without sending frames to a cloud inference API, although the caller remains responsible for the rest of the media workflow.

  • Parameters are validated before processing

    Thresholds, kernel sizes, colors, and numeric ranges are checked so invalid configuration fails early instead of producing undefined transformations.

  • End-of-stream state is cleared

    The stream path releases its capture and removes stale cached frames so consumers do not mistake the last frame for continuing live input.

Key engineering decisions and tradeoffs

Define a detector contract instead of coupling the pipeline to one model
Why: lets the same masking and streaming logic work with different compatible detectors and label mappings. Tradeoff: detector outputs must be normalized consistently, and quality varies by model.
Keep masking strategy independent from detection
Why: downstream requirements may call for blur, pixelation, or full occlusion using the same detections. Tradeoff: callers must choose a treatment whose reversibility and visual utility match the risk.
Run inference locally
Why: avoids making cloud upload a prerequisite and can reduce network exposure and latency. Tradeoff: throughput and model choice depend on local hardware, runtime, resolution, and workload.
Support optional ensembles and regional detectors
Why: a general object detector does not cover every plate, document, text, or script-specific case. Tradeoff: additional detectors increase compute cost and can introduce overlapping or conflicting regions.
Separate pixel masking from metadata removal
Why: changing visible regions does not remove file metadata or other non-pixel information. Tradeoff: a complete media-handling workflow must compose both operations deliberately.
Expose profiling instead of claiming universal speed
Why: real performance depends on the detector, input size, stream, hardware, and masking configuration. Tradeoff: every deployment needs its own reproducible benchmark.

Verification and known failure modes

  • Detection and core tests

    Public tests exercise detector output, target selection, orchestration, anonymization methods, and the core media-processing contract.

  • Stream lifecycle tests

    End-of-file, capture release, cached-frame cleanup, and background-reader behavior are verified so stale data is not presented as a live frame.

  • Regional-path tests

    Arabic and multiscript utilities, regional detector behavior, and related quality fixes are tested separately from the general object path.

  • Operational hooks

    Batch processing, profiling, monitoring, audit logging, custom regions, and metadata handling are optional components around the core pipeline.

  • Known limit

    Occlusion, motion blur, small regions, difficult angles, domain shift, incorrect labels, and unsupported objects can produce missed or incorrect masks.

  • Benchmark boundary

    A historical controlled run reached approximately 25–30 FPS, but the retained record does not define enough of the configuration to reproduce it or generalize it to specific hardware.

PrivacyGuard is an independently built masking component with public code and tests. It is not presented as automatic legal compliance, a guarantee that every sensitive region is detected, or proof that a processed file is safe for every downstream use.

Deployment context

I built PrivacyGuard independently as one component inside a larger CCTV system for a freelance client. It has been used with real footage, but the client, system, recordings, and operational details are confidential and are not reproduced here.

What the claim does—and does not—mean

Masking quality depends on detection quality. Missed or heavily occluded regions cannot be masked, blur is not encryption, and this project is not presented as automatic legal compliance. A historical controlled internal run reached approximately 25–30 FPS, but the retained project record does not define enough of the configuration to reproduce or generalize it. The result is not attributed to Raspberry Pi 4, a $35 computer, or arbitrary hardware.
